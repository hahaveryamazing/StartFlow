# V2 → V3 升级与回退

## 实际基线

V2 历史提交 `16de7f5` 与标签 `startflow-v2.0-baseline` 保留；V3 在 `codex/startflow-v3` 增量开发。保留原应用标识 `com.startflow.desktop`、用户数据目录和既有 V1 / V2 数据表。没有删除或改写整个项目。

数据库版本 2 → 3；V1 可依次经过 1 → 2 → 3。内部旧 Config 和 Workflow 仍为版本 1；新增 Automation / Context 各有 Schema 1；外层 JSON 备份版本 3。读取旧 JSON 包继续使用兼容转换，新旧实体通过稳定 UUID 关联。

## 迁移流程

1. 正常打开原库，拒绝未知和高于支持版本的数据库。
2. 使用 SQLite Backup API 创建一致性副本，包括 WAL 中已提交的数据；失败则停止升级。
3. 在事务中新增 V3 模式、规则、快照、事件、持久化事件声明、配置版本、评估记录、决策、冷却、覆盖和 AI 草稿表及索引。
4. 检查外键，写入迁移版本与升级备份记录，提交事务。
5. 清理上一进程未完成执行状态为 interrupted，不重放已启动动作；保留自动自然日 / 事件去重声明。

旧场景、共享任务、顺序、计划、工作流、布局、快捷键、主题、执行日志保持原值。新设置有安全默认值：智能自动化、Wi-Fi、持续进程检测、指定服务探测和 AI 关闭；显示器、电源、当前会话状态允许读取。Windows 登录自启不因升级改变。

## 验证证据

`src-tauri/tests/fixtures/v2-populated.sql` 固化实际 V2 隔离运行产生的非空库。Rust 集成测试逐表比较迁移前后数据与升级备份；原生测试读取旧场景、任务、计划、工作流、布局、快捷键和日志。迁移异常测试验证 DDL 与版本回滚、原始数据保留。

本机已运行 V3 NSIS 对真实 V2 安装目录进行升级，核对配置、执行历史、自启状态、目录和完整 V2 扩展，再启动一次验证持久化。见 [安装证据](v3-installer-results.json)。这些测试不代表物理重新登录和所有硬件环境已验收。

## 导入与设备迁移

导入先验证结构、版本和所有引用，显示预览；支持合并 UUID 重映射和完整替换二次确认。恢复前创建备份，事务写入，再做完整性检查。导入不执行工作流，暂停自动任务；新增敏感权限、AI、导入规则和快捷键按安全策略关闭，用户再逐项启用。

升级 SQLite 副本含旧历史；常规 JSON 备份含配置与管理的背景图片，不自动包含运行日志。JSON 不包含 AI 密钥。信任网络保存的 DPAPI 密文不能保证在其他用户 / 设备解密；导入后显示未知并要求重新配置。应用路径在其他电脑可能不存在，需要用户修正。

## 失败和回退

迁移失败保留原库并报错，不创建空数据库替代。备份通常在实际数据目录的 `backups/upgrade-UUID.sqlite3`，通过记录确认其原始 Schema。

需要回退时，先彻底退出 StartFlow，保留当前 V3 数据目录的完整副本，再安装原 V2 程序并使用迁移前 **版本 2** 的 SQLite 备份副本恢复；不要让 V2 打开版本 3 的数据库。数据库的 `-wal` / `-shm` 与主文件应在程序退出后统一处理，不把旧 WAL 与恢复副本混用。管理的背景图片另行保留。回退会丢失升级后新增的配置，先导出 V3 备份留存。

卸载默认保留当前用户配置；只有明确选择删除应用数据才删除。API Key 由 Windows Credential Manager 保存，可在 AI 设置主动删除。
