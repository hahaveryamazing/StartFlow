# StartFlow V3.1 第一阶段：安全凭据管理

本阶段基于 V3.0 提交 `299230e`，在 `codex/startflow-v3.1-credentials` 分支增量实现。只管理账号与密码，不提供自动登录、不启动绑定目标、不改变 Windows 登录账号。原有用户 `AGENTS.md` 保留。

## 检查基线与兼容范围

- 开始时 Git 原有跟踪文件无未提交改动；保留 V1/V2/V3 提交历史及 V3 稳定安装包。
- 沿用 Tauri 2 + Rust + React/严格 TypeScript + SQLite。实际原库版本为 3；任务执行器、工作流、调度、托盘、快捷键、窗口布局、环境规则、AI、主题和备份均继续复用。
- Tauri 应用标识 `com.startflow.desktop`、窗口名称、CSP 和已有 capabilities 不变。没有增加凭据读取插件权限，没有使用 Shell 或管理员权限。
- 生产应用数据目录通常为 `%APPDATA%\com.startflow.desktop`；本阶段原生测试使用独立临时目录和合成数据，未升级或覆盖生产数据库，未替换已安装的应用。

## 实现内容

账号字段：UUID、名称、用户名、网页/应用类型、关联目标、凭据引用 UUID、时间与乐观并发版本号。网站规范化为 http/https origin，拒绝内嵌用户名/密码、查询参数、片段和控制字符；应用目标为本地绝对 EXE/LNK 路径，可绑定尚未安装的目标，但不执行它。一个网站/应用支持多个不同账号，不对目标施加唯一约束。

「账号与凭据」页面支持新增、编辑、删除确认、搜索、类型筛选、存在性检查、缺失/不可访问状态、清理重试、加载/空状态/错误显示。沿用全部深浅主题变量、密度与圆角。编辑时不读取或回填原密码；留空保留，输入新密码替换。密码不进入 Zustand、React 表单状态或浏览器存储，提交结束及取消时清空输入，防止重复提交。

后端使用 Windows `CredWriteW` / `CredReadW` / `CredDeleteW`，`CRED_TYPE_GENERIC` 和 `CRED_PERSIST_LOCAL_MACHINE`。这是当前 Windows 用户在本机的通用应用凭据，不是系统登录密码，也不是机器上所有用户共享。专用命名空间为 `StartFlow.V3.1.Account.<UUID>`，不访问 V3 AI 凭据或其他应用凭据。Windows Vault 中只存密码，账号用户名以 SQLite 元数据为准。

SQLite **不存密码、密码密文或密码摘要**。Rust Secret 仅反序列化，不实现 Debug、Serialize 或 Clone；使用 zeroize 在退出作用域时清理持有的 Rust 字符串/字节缓冲区。检查存在性时不向业务层返回密码，清理 Windows 分配的读取缓冲区后 `CredFree`。非 Windows 环境明确返回不支持，不使用模拟安全存储替代生产能力。

## IPC 安全边界

| 命令 | 请求 | 返回 |
|---|---|---|
| accounts_list | 无 | 账号元数据、saved/missing/unavailable、待清理数量 |
| accounts_save | 元数据、可选写入密码、expected_revision | 元数据与待清理数量 |
| accounts_delete | 账号 ID、expectedRevision | 待清理数量 |
| accounts_exists | 账号 ID | 布尔值或明确错误 |
| accounts_retry_cleanup | 无 | 待清理数量 |

无读取、展示、复制、导出密码接口。凭据引用只能由后端生成，写入 Schema 拒绝额外字段。查询只能通过当前库中的账号 ID 解析引用，不能查询任意系统凭据。所有命令验证调用 WebView 为 main 且来源为精确的本地 Tauri origin；调试构建额外允许配置的本地 Vite 地址，发行构建不允许。快速命令面板和远程 origin 被拒绝。系统调用在阻塞工作线程执行，账号写入使用互斥锁和整型 revision 阻止过期编辑覆盖。

Windows Credential Manager 属于 Windows 用户安全边界，同一用户权限的其他程序可能访问该用户凭据；本实现不是对抗同用户恶意进程的独立密码库，也没有主密码。前端输入及 IPC 必然暂时持有用户刚输入的密码，JavaScript 字符串无法保证物理内存清零；不宣称密码从未进入内存。默认无遥测或外部凭据上传。

## 数据迁移与跨存储一致性

数据库版本 **3→4**，新增 `credential_accounts` 和 `credential_cleanup`（仅引用 ID）及目标索引。原表不删除、不重写。已有库先用 SQLite 在线备份 API 创建一致性升级备份，再事务建表、外键检查、记录版本及备份。备份失败停止升级；DDL/校验失败回滚；不能把用户原库清空重建。V1→4、V2→4、V3→4 均有迁移覆盖；非空 V2/V3 样本来自此前真实隔离原生测试，不含生产用户数据。

Windows 凭据库和 SQLite 不能共享事务，因此更新密码使用引用轮换：

1. 持久化新引用的清理记录。
2. 写入新的 Windows 凭据，旧密码不变。
3. 事务提交新账号引用，移除新引用清理标记，将旧引用排入清理。
4. 删除旧凭据；若失败显示待清理数量，提供重试并在下次启动恢复。

数据库失败会保留旧账号/旧密码并清理新孤立凭据。崩溃留下的孤立引用可恢复清理；仍被账号使用的引用不会被清理。删除也先持久化清理记录再调用 Windows，失败不会伪称密码完全删除。

普通 JSON Config/Bundle 维持 Schema 3，**账号与凭据不进入此导出格式**。普通配置导入/完整替换保留账号表。SQLite 升级备份仅含账号元数据，不包含密码。复制/回退数据库不会复制或恢复对应 Windows 密码；跨设备或恢复旧引用后显示 missing，需要重新输入。卸载依旧保留用户数据及用户凭据；可在卸载前从本页面主动删除。
